# 0006. Multi-turn cases with a scripted history

- Status: proposed
- Date: 2026-10-20

## Context

Every case today is a single user message. Most agents in production are
conversations: the answer that matters depends on what was said before (a name
given three turns earlier, an option the assistant offered, a correction from the
user). A suite that can only send one message cannot test that the model uses the
conversation it is given.

There are two ways to evaluate a conversation. The earlier assistant turns can be
**written by hand** in the suite, so only the final answer comes from the model,
or they can be **generated by the model** turn after turn. The second follows a
different path on every run, so it cannot be recorded, replayed in CI or
compared case by case.

## Decision

A case can give its input as `turns`, a list of messages with roles `user` and
`assistant`, instead of `input`. Every turn is sent as written; the model produces
only the answer to the last user turn, and only that answer is scored against
`expect`. Everything that identifies or reports a case (id, tags, recordings,
reports, `compare`) stays the same.

### Suite format

```yaml
name: workshop-booking
description: Book repair slots for a bike workshop. All customers are fictional.
threshold: 0.8
system: |
  You book repair slots for a bike workshop. Offer only the slots you are told
  about, keep the customer's details from earlier in the conversation and confirm
  bookings in one sentence.

cases:
  # A conversation: the model writes only the reply to the last user turn.
  - id: confirm-chosen-slot
    turns:
      - role: user
        content: Hi, my name is Laura Pérez. My rear brake is rubbing, can I bring the bike in?
      - role: assistant
        content: Of course, Laura. I can offer Tuesday at 10:00 or Thursday at 17:30.
      - role: user
        content: Thursday works. Please confirm the booking with my name.
    expect: { type: contains, values: [Laura, Thursday, "17:30"] }
    tags: [booking, memory]

  - id: correction-wins
    turns:
      - role: user
        content: I'd like to book a puncture repair for Marc Soler on Tuesday at 10:00.
      - role: assistant
        content: Done, Marc. You're booked for Tuesday at 10:00.
      - role: user
        content: Sorry, I meant Thursday at 17:30. What time is my booking now?
    expect: { type: regex, pattern: "(?i)thursday.*17:30" }
    tags: [booking, correction]

  # A single message still uses `input`, exactly as before.
  - id: opening-hours
    input: What time do you open on Saturdays?
    expect: { type: contains, values: ["Saturday"] }
    tags: [faq]
```

### Validation rules

The suite is rejected when it is loaded (exit code `2`, Pydantic error that names
the case) if a case breaks any of these rules:

1. A case has exactly one of `input` or `turns`.
2. `turns` has at least one turn, and every `content` is a non-empty string.
3. `role` is `user` or `assistant`. There is no `system` role in `turns`: the
   system prompt stays at suite level, so all cases in a suite share it.
4. The first turn is from the user and roles alternate (`user`, `assistant`,
   `user`, ...).
5. The last turn is from the user, because the model is asked to answer it.
   An assistant turn at the end would be a pre-filled answer, which current
   models do not all support and which would be scored as if the model wrote it.

Rules 4 and 5 together mean a valid conversation always has an odd number of
turns.

### Compatibility

`input` keeps working with no change. Internally, a case exposes its
conversation as a list of messages; a case with `input: "..."` becomes a single
user turn. Providers, the runner and the scorers read that list, so there is one
code path for both forms. Existing suites, recordings and JSON reports remain
valid, and the `Provider` protocol (`complete(system, case)`) does not change.

### How the conversation reaches each provider

| Provider | Request |
| --- | --- |
| OpenAI (Responses API) | `input` becomes a list of `{"role": ..., "content": ...}` messages in order; the system prompt stays in `instructions` |
| Anthropic (Messages API) | `messages` gets the same list in order; the system prompt stays in `system` |
| Replay | Unchanged: looks up the recorded answer by case id |

Both APIs accept `user` and `assistant` messages with text content in a single
request, so no server-side conversation state (such as OpenAI's
`previous_response_id`) is used. Every call is stateless and the request is
fully defined by the suite file.

Reported `input_tokens` include the whole history, so a long conversation costs
more than its last message suggests. That is the real cost of the call and is
reported as such.

### Replay and `--record`

Recordings stay keyed by case id, and each entry is the model's final answer
only. The scripted turns are already in the suite, so recording them again would
duplicate them. A recording made with `--record` therefore looks exactly like
today's:

```yaml
confirm-chosen-slot: Booked, Laura. Thursday at 17:30.
correction-wins: Your booking is now Thursday at 17:30, Marc.
opening-hours: On Saturday we open at 9:00.
```

If the turns of a case change, its old recording no longer answers the same
conversation. As today with `input`, the recording has to be refreshed with a new
live run; the tool does not detect stale recordings.

### `compare`

Nothing changes. A conversation is one case with one id and one verdict, so it is
matched across reports and classified as a regression, fix, added or removed case
like any other (ADR 0005). The failure reason refers to the final answer.

## Alternatives considered

| Option | Why not |
| --- | --- |
| The model generates every assistant turn | Each run follows a different path: it cannot be recorded or replayed in CI (ADR 0002), and `compare` would compare different conversations under the same id |
| A simulated user (a second model plays the user) | Same problem as above, plus the simulator itself needs evaluating; better suited to a later, explicitly non-deterministic mode |
| Expectations on every assistant turn | With a scripted history the earlier turns are not model output, so there is nothing to score; the same checks can be written as separate cases that share a prefix (YAML anchors) |
| A transcript inside `input` ("User: ... Assistant: ...") | The model receives one user message, not a conversation, so roles are lost and behaviour differs from production |
| A separate `conversations:` list beside `cases:` | Duplicates ids, tags, recordings, reports and `compare` for no gain |
| Server-side state (`previous_response_id`, conversation objects) | Provider-specific, stateful and not available in the same form on Anthropic |

## Consequences

Suites can test memory, corrections and follow-ups while staying deterministic,
replayable and comparable. The scripted assistant turns may not match what the
model would have said; that is intended, because the case fixes the history and
tests the next answer. Long conversations increase token cost per case.
Scoring every turn of a model-driven conversation remains possible later as a
separate, opt-in mode with its own ADR.
